## 1. 背景與問題

`TrainingDetail.TrainingType` 目前定義兩種狀態：

- `1 = 取得證照`
- `2 = 回訓`

但「狀態的語意」與「下次回訓日（`NextReviewDate`）如何推進」兩件事互相牽動，目前存在語意衝突：

- **開發者理解**：`1` = 取得證照 **或** 回訓後更新證照；`2` = 去受訓（尚未完成更新）。
- **使用者（客戶）說法**：只有「最初取得證照」是 `1`；之後不論有沒有滿足時數，**一律是回訓 `2`**。
- **客戶的期限算法**：下次回訓日 = 某一次回訓日 + N 年。

核心難題：**在「只有第一筆是 1」的模型下，哪一筆回訓的日期可以當作新的證照起算日？** 因為有些回訓紀錄並未滿足應回訓時數，不能直接拿「最後一次回訓日」當起算日。

---

## 2. 現狀行為（程式碼）

`MappingExtensions.cs:39-105` 目前邏輯：

- `latestAcquireDate` = **最後一筆 `TrainingType == 1`（取得證照）** 的受訓日期。
- `NextReviewDate = latestAcquireDate + header.Years`（`header.Years` 為 null 則回傳 null）。
- `currentPeriodDetails` = 受訓日期 `>= latestAcquireDate` 的所有單身。
- `accumulatedHours` = 當前週期累計時數；`remainingHours = max(0, header.Hours - accumulatedHours)`。
- `OverallStatus`：已過期 > 回訓完成（remainingHours == 0）> 待回訓（NextReviewDate 在一年內）> 無。

**關鍵後果**：回訓時鐘**只在出現新的 `type 1` 紀錄時才前進**；`type 2`（回訓）紀錄永遠不會推進 `NextReviewDate`。

因此若採用客戶模型（只有第一筆是 1），現行算法會讓 `NextReviewDate` = 永遠是「最初取得日 + N 年」，第一個週期之後即永久逾期。**此算法對客戶模型是壞掉的。**

---

## 3. 核心概念：回訓週期與「回訓完成日」

不論採用哪個方案，都需要一個共同的「回訓完成日」判定規則。

定義（roll-forward 週期演算法）：

> 在一個週期內，將回訓紀錄**依受訓日期排序累加時數**；**累計第一次達到應回訓時數 H 的那一筆，其受訓日期 = 本週期完成日 C**。
> 下一個週期的起算日（anchor）= C，下次回訓期限 = C + N 年；接著從 C 之後的紀錄重新累加，推導下一個週期。

- 未讓累計跨過門檻 H 的回訓，只是「累積中」，**不推進期限**。
- 此規則正面解決「有些回訓沒滿足時數」的疑慮：只有讓累計達標的那一筆才推進週期。

### 演算法（虛擬碼）

```text
anchor = 初始取得證照日 (type 1 那筆)
H = header.Hours          // 應回訓時數
N = header.Years          // 回訓週期年數
sessions = 所有 type 2 紀錄，依日期排序
acc = 0
completedCycles = []      // 每個元素為 (完成日 C)

for s in sessions where s.date >= anchor:
    acc += s.Hours ?? 0
    if acc >= H:
        C = s.date
        completedCycles.append(C)
        anchor = C
        acc = acc - H        // 已確認：超額滾入下一週期（§6 規則2-A）

latestAnchor = completedCycles.last ?? 初始取得證照日
NextReviewDate = latestAnchor + N 年
remainingHours = max(0, H - acc)   // acc 為當前未完成週期的累計
```

## 4. 方案比較

| | 方案1（現狀＋自動產生更新紀錄） | 方案2（純推導，使用者說法） | 方案3（表頭物化 anchor） |
|---|---|---|---|
| **狀態碼** | 1=初始, 2=回訓, **新增 3=證照更新（自動產生）** | 1=初始, 2=全部回訓 | 1=初始, 2=全部回訓（狀態純描述性） |
| **完成日 C 存哪** | 寫一筆 detail（status 3）到 TCSTB | 不存，讀取時即時推導 | 存到表頭（或小週期表），SaveChanges 時重算 |
| **NextReviewDate 算法** | 沿用現狀（anchor = 最後一筆 1 或 3） | 讀取時跑 §3 roll-forward 演算法 | 讀取時直接用表頭存的 anchor + N |
| **優點** | 有明確軌跡；對現算法改動最小 | 資料最乾淨、零 schema 變更、最貼近使用者心智、改紀錄後自動正確 | 有審計軌跡又無合成資料；過去週期可凍結；讀取不必重算 |
| **缺點** | 合成 detail 與使用者輸入混雜；**PK=(員工,證照,日期) 會與觸發那筆撞號**；刪改歷史紀錄須連帶重生合成列，同步複雜 | 演算法需完整單元測試；`header.Hours` 若事後變更，過去週期會**追溯重切**（亦可視為「永遠反映現規則」的優點） | 多一欄位/小表；須在 SaveChanges 攔截器內重算（邏輯同方案2，多一層持久化） |

## 5. 建議方案

**主推方案2（純推導）**，理由：

1. 完全符合使用者說法（只有第一筆 = 1），資料最乾淨，不必變更 schema。
2. 每張表頭的 detail 筆數少，讀取時即時推導成本可忽略。
3. 編輯／刪除任何回訓紀錄後，期限自動正確，無需維護合成列。
4. 方案1 的 PK 撞號（完成日 C 當天本就有一筆觸發它的回訓）是硬傷，須改 PK 或日期 +1 天，皆不理想。

**方案3 作為「需要凍結歷史／審計」的升級版**：演算法與方案2 相同，僅將推導結果存在**表頭**（避開 detail 的 PK 問題）。若客戶要求「過去每個週期的完成日固定、不因日後改時數而變動」，再升級至方案3。

## 6. 已確認規則

> 以下規則影響 §3 演算法行為，已於 2026-06-04 與使用者確認定案。

1. **提早達標**（採 A）
   在期限前就累積滿時數，下次期限基準為何？
   - **採 A：達標日 + N 年**（會提早；符合客戶「回訓日 + N 年」說法）。
   - 替代（B）：原期限 + N 年（維持原節奏）。

2. **超額時數**（採 A）
   跨過門檻那一筆若超額（例如需 8 小時、該筆讓累計變 10），多出的時數如何處理？
   - **採 A：滾入下一週期**（`acc = acc - H`），多出的時數計入下一週期累計。
   - 替代（B）：歸零（`acc = 0`），每週期獨立。
   - §3 虛擬碼已依此定案寫為 `acc = acc - H`。

3. **單一 type 1 不變式**（新增邏輯前提）
   §3 演算法假設「每張表頭恰好一筆 type 1 當 anchor，其餘全為 type 2 累加」。若出現第二筆 type 1，該筆既不當 anchor 也不被當 session 累加，時數會被忽略、anchor 不前進 → 推導錯誤。故新增／編輯邏輯須維持此不變式：
   - **首筆必須是 type 1（取得證照）**：`AddDetailAsync` 已有守則（line 132-134）。
   - **第二筆起必須是 type 2（回訓）**：`AddDetailAsync` 須補反向守則，header 已有 detail 時拒絕 `type == 1`。
   - **新增 UX（採自動推導並鎖定）**：前端依「是否為第一筆」自動決定類型並鎖定 radio（首筆鎖「取得證照」、其餘鎖「回訓」），使用者不可手選，避免選錯。
   - **編輯類型（採鎖定不可改）**：編輯時 `TrainingType` 唯讀（首筆永遠 1、其餘永遠 2），`UpdateDetailAsync` 不得改變 type，避免事後破壞不變式。
   - 此「其餘必須 2」屬有狀態規則，置於 service 層（同首筆守則）；驗證器僅做格式驗證。

## 7. 方案2 範例說明

> 統一假設：應回訓時數 **H = 8 小時**、回訓週期 **N = 3 年**、初始取得證照日 = `2020-01-01`。
> 依 §6 定案：提早達標採 A（達標日 + N 年）、超額時數採 A（滾入下一週期 `acc = acc - H`）。

### 情境1：只有初始取得，無任何回訓
| type | 日期 | 時數 |
|---|---|---|
| 1 | 2020-01-01 | — |

- 累計 acc = 0
- **NextReviewDate = 2020-01-01 + 3 = `2023-01-01`**
- **remainingHours = 8 - 0 = `8`**

### 情境2：有回訓，但累計未達標
| type | 日期 | 時數 | 累計 acc |
|---|---|---|---|
| 1 | 2020-01-01 | — | 0 |
| 2 | 2021-03-01 | 3 | 3 |
| 2 | 2022-05-01 | 3 | 6 |

- acc = 6 < 8 → **未達標，期限不推進**
- **NextReviewDate = `2023-01-01`（仍為初始取得 + 3）**
- **remainingHours = 8 - 6 = `2`**
- 重點：沒滿足時數的回訓只是「累積中」，不會把證照起算日往前推。

### 情境3：累計剛好達標（完成一個週期）
| type | 日期 | 時數 | 累計 acc | 事件 |
|---|---|---|---|---|
| 1 | 2020-01-01 | — | 0 | anchor |
| 2 | 2021-03-01 | 3 | 3 | 累積中 |
| 2 | 2022-05-01 | 5 | 8 | **達標！C = 2022-05-01** |

- 跨過門檻那筆（2022-05-01）即為本週期完成日 C
- anchor 前進到 `2022-05-01`，滾入後 acc = 8 - 8 = 0
- **NextReviewDate = 2022-05-01 + 3 = `2025-05-01`**
- **remainingHours = `8`**

### 情境4：連續多個週期達標
| type | 日期 | 時數 | 累計 acc | 事件 |
|---|---|---|---|---|
| 1 | 2020-01-01 | — | 0 | anchor |
| 2 | 2021-03-01 | 3 | 3 | 累積中 |
| 2 | 2022-05-01 | 5 | 8 | **C1 = 2022-05-01**，acc 滾入後 = 0 |
| 2 | 2023-06-01 | 8 | 8 | **C2 = 2023-06-01**，acc 滾入後 = 0 |

- anchor 逐次前進：2020-01-01 → 2022-05-01 → 2023-06-01
- **NextReviewDate = 最後完成日 + 3 = 2023-06-01 + 3 = `2026-06-01`**
- **remainingHours = `8`**

### 情境5：達標後又有回訓，但未達下一週期門檻
| type | 日期 | 時數 | 累計 acc | 事件 |
|---|---|---|---|---|
| 1 | 2020-01-01 | — | 0 | anchor |
| 2 | 2022-05-01 | 8 | 8 | **C1 = 2022-05-01**，acc 滾入後 = 0 |
| 2 | 2024-01-01 | 4 | 4 | 累積中（下一週期） |

- **NextReviewDate = 2022-05-01 + 3 = `2025-05-01`（不變）**
- **remainingHours = 8 - 4 = `4`**

### 情境6：提早達標（規則1採 A）
- 原期限本應為 `2023-01-01`（初始 + 3），但在 2022-05-01 就累計達標。
- 採 A：新期限以**達標日**為基準 → `2022-05-01 + 3 = 2025-05-01`（比原期限提早，符合客戶「回訓日 + N 年」說法）。

### 情境7：超額時數（規則2採 A，滾入）
| type | 日期 | 時數 | 累計 acc | 事件 |
|---|---|---|---|---|
| 1 | 2020-01-01 | — | 0 | anchor |
| 2 | 2021-03-01 | 6 | 6 | 累積中 |
| 2 | 2022-05-01 | 5 | 11 | **達標！C = 2022-05-01**，超額 3 |

- 跨門檻那筆讓 acc 從 6 → 11（超額 3 小時）。
- 採 A（滾入）：`acc = 11 - 8 = 3`，多出的 3 小時計入下一週期。
- **NextReviewDate = 2022-05-01 + 3 = `2025-05-01`**
- **下一週期 remainingHours = 8 - 3 = `5`**（只需再回訓 5 小時即可達標）。

### 情境8：`header.Years` 為 null
- **NextReviewDate = `null`**（不崩潰），remainingHours 照常計算。

## T1 — 受訓紀錄：點擊「員編」「證照」欄位標題排序

> 目前受訓單頭列表完全沒有排序功能。
> `TrainingService.GetHeadersAsync` 於記憶體中組完 `TrainingHeaderDto` 清單後直接 `PaginationHelper.Paginate`，
> 排序需在 Paginate **之前**套用，否則只會排到當頁資料。

### 設計（2026-07-08 修訂：預設證照排序 + 雙鍵排序）

- 排序參數走 `TrainingSearchQuery`，與快速搜尋、進階搜尋皆可並存
- `SortBy` 允許值：`EmployeeId`、`LicenseType`；非白名單值回落預設排序
- **預設排序：證照升冪**（未指定 SortBy 亦同）
- **雙鍵排序**：主排序切換時，另一欄自動為次要排序（固定升冪）——
  依員編排序時同員編再依證照排；依證照排序時同證照再依員編排
- 同欄位再點一次切換主鍵升冪/降冪（次要排序維持升冪）
- **證照採自然排序**（2026-07-08 修正）：`1.1 → 3.2 → 11.2 → 16.3 → 20.1`，非字串排序
  （字串排序會錯排成 `1.1 → 11.2 → 16.3 → 20.1 → 3.2`）。
  原邏輯存在於 `LicenseService.NaturalSortKey`（private），抽出為共用
  `src/TCS.Core/Helpers/LicenseTypeSort.NaturalKey`，證照管理與受訓排序共用同一實作，
  兩頁排序保證一致

### 設計考量：CRUD 維護入口放在本頁（2026-07-08 討論定案）

**議題**：總覽頁做成唯讀，使用者會不會預期「在這裡直接維護」？

**結論：第一階段就內建 CRUD，本頁成為廠別需求的唯一維護入口**，理由：

1. **使用者心理預期** — 使用者預期在「看得到資料的地方」直接操作；廠別視角頁面唯讀會產生
   「那我要去哪改？」的困惑（此為本議題的起因）
2. **維護動線跟著思考單位走** — 實務情境是「A1 廠盤點：堆高機 3 人、天車 2 人」，
   在本頁「選廠 → 逐筆加證照」一氣呵成；在證照管理做同一件事要逐張證照跳頁操作
3. **避免尷尬中間態** — 先上唯讀版，等於：使用者困惑一輪 → 改版加 CRUD → 使用者重新學一次；
   不如第一版直接做進去
4. **成本不高** — 後端 CRUD API 已存在（`api/licenses/{licenseType}/plants`，
   `LicensePlantRequirementController`），本頁直接呼叫即可，後端零改動；
   前端照 `license.js` 廠別需求子表模式做 modal，權限沿用 `TcsAuth.applyButtonGuards` + 既有 `[RequireAction]`

**配套原則：維護入口只能有一個** — 同一份資料兩套編輯 UI 是最差方案
（使用者不確定該去哪改、表單邏輯與測試要維護兩份）。
故證照管理單身**降級為唯讀檢視**（檢視價值仍在：選證照順便看哪些廠需要），並加提示導向本頁維護。

**待與使用者確認**：是否存在「證照驅動」的維護情境（如新開證照時順手設定適用廠別）？
若有，改在本頁反向操作（每廠各加一筆）可完成、僅多幾個點擊，需確認使用者接受此 trade-off。

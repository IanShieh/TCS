## 觸發點

現行 `CreateTrainingHeaderValidator` 在 `IsOther=false` 時,會擋下純整數大類:

```csharp
RuleFor(x => x.LicenseType)
    .Must(lt => !ValidatorHelpers.IsLicenseTypeCategory(lt))
        .WithMessage("受訓單頭的證照類別必須為小類（含小數點）")
    .When(x => !x.IsOther);
```

使用者主張:**這個限制的兩條原始理由都已經站不住腳。**

---

## 使用者提出的兩個質疑

### 質疑 1:「大類不對應實際證照」是錯的——有些大類本身就該能被選

原 spec §4-1 假設:純整數大類 = 分類抬頭、本身不對應實際證照。
使用者反駁:實務上有些大類就是一張可頒發 / 可受訓的真實證照,應該能直接被選為受訓對象。

### 質疑 2:「沒有回訓週期計算依據」沒關係——不是所有證照都要回訓

原 spec 以「小類才保證有 Hours/Years、才算得出回訓週期」為由要求必填小類。
使用者反駁:本來就不是所有證照都需要回訓,沒有回訓週期是正常情況,不該成為限制理由。

---

## 查證結果(支持使用者的論點)

### 質疑 2 已是既成事實

`TA004 nullable` 改版後,`Hours`/`Years` 在 `LicenseMaster`(MA004/MA005)與 `TrainingHeader`(TA004)皆可為 null。
→ **連小類現在都可以「沒有回訓要求」**。「必須是小類才有回訓週期」這條理由已被系統自身的演進推翻。

### 質疑 1 撞上一個既有的設計徵用

`docs/todo-2026-05-12.md:15-16` 早有決議:

> 1. TrainingHeader 新增時,LicenseType 下拉是否包含大類 → **是,全部包含(大類 + 小類均可選)**
> 2. 選擇「其他」時,LicenseType 送出值為何 → **送大類代碼**

也就是說:**目前「在受訓單頭下拉選一個大類」這個動作,已經整個被徵用去代表「其他」**。
選大類 → 走 `IsOther` → 自填名稱存 Remark → Service 產生序號碼(`99.1`、`1.0.1`)。
所以現行系統沒有「選大類 = 受訓這張大類證照」這個語意;那個位置被「其他」佔走了。

---

## 根本問題:`LicenseType` 數字格式被超載

`LicenseType` 的整數/小數格式,目前同時被拿來表達三件本來不相干的事:

| 格式想表達的 | 是否該由格式決定 |
|---|---|
| 階層位置(父分類 vs 葉節點) | ✅ 合理 |
| 這是不是一張真實證照 | ❌ 質疑 1:有些大類就是真證照 |
| 這是不是「其他」桶 | ❌ 05-12 徵用塞進來的 |

補充:`LicenseMasterDto.IsCategory`(`LicenseMasterDto.cs:4`)看似獨立旗標,實際只是「`LicenseType` 不含小數點」的同義詞,**並未真正解耦**。

---

## 核心取捨(待使用者決定)

若要讓「大類本身可被選為真證照」,就得把**「是不是真證照」**與**數字格式**脫鉤
(常見作法:在 `LicenseMaster` 加明確旗標,如 `IsSelectable` / 葉節點標記,驗證器改查旗標而非 `!IsLicenseTypeCategory`)。

但這會與現行「選大類 = 其他」正面對撞:同一個大類,使用者選它到底是
(a) 要這張大類證照本身,還是 (b) 這分類底下的「其他」?兩種意圖必須在資料與 UI 上分得開。

### 待決選項

- **A**:被標記為可選 / 有 Hours·Years 的大類 = 真證照(直接選即建單);「其他」維持是該分類下一個獨立特殊選項。兩者並存,靠旗標區分。
- **B**:廢掉「大類 = 其他」徵用,大類就是大類(可選則可選);「其他」另尋機制或移除。
- **C**:其他模型——待使用者描述「下拉選一個大類時,系統應如何解讀」。

## 決議(2026-06-17)

採 **方案 A**:可選大類 = 真證照,與「其他」並存;但**靠「有無小類」結構規則區分,不新增旗標**。

### 判定來源
純整數大類 **+ 建單當下底下無小類 + 非保留碼 `99`** → 視為可直接選的真證照。
- 「有無小類」即時判斷(查是否存在 `Category = 該大類碼` 的小類),**零 schema 變更**。
- 依據:有些證照種類自成一格、不再往下展一層,大類本身即真證照。

### 名稱處理
一般大類/小類名稱一律由主檔 join 帶出,**不需手填、不需 Remark**。
**僅「其他」(大類或小類)** 才需記錄自填名稱。故直接選的獨立大類,行為等同一般小類。

### `99` 與「其他」
`99` 永遠走「其他」(`IsOther=true`),選它帶出下一個 `99.{n}`,排除於「可直接選」之外。
既有「其他」序號機制(`99.{n}` / `X.0.{n}`、`OtherLicenseCode`)**完全不動**。

### 下拉呈現(三分)
| 大類型態 | 呈現 | 送出 |
|---|---|---|
| 有小類(分類抬頭) | 小類清單 + 「其他（X類）」 | 小類 `IsOther=false`;其他 `IsOther=true`, base=X → `X.0.{n}` |
| 無小類且非 99(獨立真證照) | 直接一個可選 option | `IsOther=false`, `LicenseType=X`,名稱 join 帶出 |
| `99`(全域其他) | 「其他」 | `IsOther=true`, base=99 → `99.{n}` |

### 實作落點
「有無小類」需查資料,現行 `CreateTrainingHeaderValidator` 為無狀態、同步,查不了 DB。
→ 此判定落在 **Service 層**(`CreateHeaderAsync`,已有 async repo 查詢);validator 僅保留格式檢查。

### Known Issue — 大類動態翻轉
「有無小類」是動態的:某大類今天無小類(可選、可建單),日後若長出小類即變回分類抬頭。
- 判定發生在**建單當下**;翻轉後**不追溯作廢**先前已建的裸碼 `X` 單頭(建立時合法、主檔 X 列仍在、名稱照樣 join)。
- 翻轉後新單須改走小類。
- **接受此行為,列為 known issue**;若日後需「一旦用過即永久可選/不可降為抬頭」,再回到顯式旗標方案。
